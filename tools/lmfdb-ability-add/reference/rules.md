# lMfDB 能力追加ルール集

このファイルが能力追加作業の唯一の正典。ClaudeCode の Skill
(`.claude/skills/lmfdb-ability-add/SKILL.md`) と Codex の `AGENTS.md` は
どちらもここを参照する。

---

## 0. 大前提

- **`index.html` 一枚に全機能が入った PWA**。CSS も JS もデータも全部この中。
  ビルド工程は無く、push したものがそのまま GitHub Pages で公開される。
- したがって **`index.html` を壊す＝サイトが落ちる**。必ず
  `check.sh` を通してからコミットする。
- 能力データは `const ABILITIES = [ ... ];` という**1行の巨大な JSON 配列**。
  手で編集せず、必ず `add_ability.py` を使う。

### 触ってはいけないもの

| 対象 | 理由 |
|---|---|
| `ABILITIES` の閉じ括弧直後に並ぶ大量の `;` | 歴史的経緯で存在する。消すと差分が汚れる |
| 既存能力の `id` | localStorage の `mf_overrides` / マイセットが id を参照している |
| `DATA_FIXES` の既存エントリ | 過去の誤記を補正するパッチ。新規追加では使わない |
| `icon-192.png` / `icon-512.png` / `sw.js` / `manifest.json` | 能力追加作業では対象外 |

## 1. データ構造

1件は次の形。**キーの順序もこの通り**に揃える（`add_ability.py` が自動で揃える）。

```json
{
  "id": 1153,
  "name": "横一閃 III",
  "desc": "[前半]＜白＞技発動時、ちからステ＜＋４０％＞",
  "card": "ロクショウ",
  "tags": ["前半", "オーラ白", "攻撃強化"],
  "source": "イベント",
  "rarity": "SSR"
}
```

### id

- **既存の最大 ID + 1** から採番する（現在の最大は 1152）。
- 欠番が 25 個あるが**再利用しない**。削除済み能力の跡。
- 既存データは 1箇所だけ昇順が崩れている（283 の次が 275）。これは既存由来なので
  直さない。新規は常に末尾へ追加する。

### name

- 同一能力の強化段階は末尾に **半角スペース + ローマ数字**（` I` / ` II` / ` III` / ` IV`）。
- 別カードで同名の能力が存在するのは**正常**（`name` は一意ではない）。
  一意なのは `id` だけ。`name × card` の組が重複していたら要確認。

### desc

- **改行は `<br>`**。生の改行・タブは入れない（JSON が1行のため壊れる）。
  `<br/>` や `<BR>` は使わない。
- 箇条書きは `<br>・` で始める。

  ```
  [自身黒]次の効果が発動<br>・相手の攻撃ステータス＜１５％＞減少<br>・[有利]ガッツ回復を停止
  ```

- **数値・記号は全角**にそろえる（既存データの慣習）。
  `＜１５％＞` `＜＋３０％＞` `＜１回＞` のように、
  数値を `＜ ＞` で囲むのがゲーム内表記に合わせた書式。
- 発動条件は先頭に `[ ]` で並べる: `[前半][自身白または無機]…`
- オーラ名は `＜白＞技` `＜黒オーラ＞` のように `＜ ＞` で囲む。
- **`</script` を含む文字列は絶対に入れない**（インライン script が閉じてページが壊れる）。

### card

- ゲーム内のカード名を正確に。同名別バージョンは `アイリス(ライバル)` `アインズ(SSR)` の
  ように **半角括弧**で区別する。
- 新規カードは `SSR_CARDS` / `MR_CARDS` / `SR_CARDS` のいずれかにも追加が要る
  （`add_ability.py` が自動でやる）。ここに載っていないと「所持」画面に出ない。
- ただし `source` が `EXトレ` / `伝授` のカードは**リスト管理対象外**（自動で除外される）。

### source

`イベント` / `閃き` / `EXトレ` / `伝授` の4種のみ。他の値はエラー。

| 値 | 意味 | 件数の目安 |
|---|---|---|
| `イベント` | イベント入手 | 最多 |
| `閃き` | 育成中の閃き | 2番目に多い |
| `EXトレ` | EXトレーニング | 少数 |
| `伝授` | ボスからの伝授 | 少数 |

同じ `name` で入手経路が複数ある場合、UI 側（`srcsByName`）が名前で束ねて
バッジをまとめて出す。**別レコードとして両方登録してよい**。

### rarity

`SSR` / `MR` / `SR` / `その他` の4種のみ。**省略不可**。

- 原則として **カードのレアリティをそのまま入れる**。同じカードの能力は
  全部同じ `rarity` になる。`[状態変化]` 系の能力も例外ではない。
- 同名の能力が別カードにある場合、`rarity` はカードごとに違ってよい
  （例: `超本気` は ミリム・リゾート=SSR / タナトス=MR / アインズ(SSR)=SSR）。
- `その他` は通常のガチャカード以外の特殊枠。現状は次の3種:

  | カード名の形 | 例 |
  |---|---|
  | `〇〇(育成論)` | `シエナ(育成論)` `サフィン(育成論)` `ポルツ(育成論)` |
  | `[ボス]〇〇(距離)` | `[ボス]ヒノトリ(零)` `[ボス]ムー(中)` |
  | `〇〇(天星翼-△△)` | `ミカ(天星翼-六英雄)` `ルーカス(天星翼-六天将)` |

  `(育成論)` カードの能力は16件すべて `その他`。

> **`rarity` を省略してはいけない理由**
> DB画面のレアリティタブは、SR を「`MR` でも `SSR` でも `その他` でもないもの」
> という消去法で絞っている（`index.html` の `dbRarityFilter` 判定）。
> つまり `rarity` が無い能力は **SR タブに紛れ込み、本来の MR/SSR タブから消える**。
> 過去に id=1120 / 1128 / 1144 の3件がこの状態だったため、2026年8月に補完済み。
> `check.sh` は現在 `rarity` 欠落を**エラー**として弾く。

### tags

- 検索フィルタに直結する。**既存タグに無い語を勝手に作らない**。
  既存タグ一覧は `scripts/lmfdb_common.py` の `KNOWN_TAGS`（現在55種）。
- どうしても新タグが要るときは
  1. `KNOWN_TAGS` に追加し、
  2. `add_ability.py` に `--allow-new-tags` を付ける。
- 表記ゆれに注意（よくある間違い）:

  | ✗ | ○ |
  |---|---|
  | `白オーラ` | `オーラ白` |
  | `命中アップ` | `命中強化` |
  | `クリ` / `クリ率` | `クリティカル` |
  | `ダメージ軽減` | `被ダメ軽減` |
  | `追撃・連撃` | `追撃連撃` |

- `オーラ白` は「白オーラ技に反応する」、`自身白` は「自身が白のとき」で**別物**。
  desc に `[自身白]` とあれば `自身白`、`＜白＞技` とあれば `オーラ白`。
- タグは重複させない。順序は自由だが、既存は
  「発動条件系 → 種族/オーラ系 → 効果系」の並びが多い。

## 2. 作業手順

```bash
# 0) 最新化（必ず先にやる）
git pull --rebase origin main

# 1) 追加内容を JSON にまとめる
cat > /tmp/new.json <<'JSON'
[
  {
    "name": "横一閃 III",
    "desc": "[前半]＜白＞技発動時、ちからステ＜＋４０％＞",
    "card": "ロクショウ",
    "tags": ["前半", "オーラ白", "攻撃強化"],
    "source": "イベント",
    "rarity": "SSR"
  }
]
JSON

# 2) まず dry-run で確認
python3 tools/lmfdb-ability-add/scripts/add_ability.py --json /tmp/new.json --dry-run

# 3) 問題なければ書き込み
python3 tools/lmfdb-ability-add/scripts/add_ability.py --json /tmp/new.json

# 4) チェック（「✅ 全項目クリア」が出るまで直す）
bash tools/lmfdb-ability-add/scripts/check.sh index.html

# 5) ★ここでユーザーに内容を提示して承認を取る★

# 6) 承認後のみ commit + push
bash tools/lmfdb-ability-add/scripts/git_commit_push.sh "add: ロクショウの能力を追加"
```

`add_ability.py` は書き込みと同時に、画面下の
`更新: YYYY/MM/DD ／ N件` 表示の**日付と件数を自動で更新**する。
日付を変えたくないときは `--no-date-update`、明示指定は `--date 2026/07/01`。

## 3. コミット規約

既存の履歴に合わせる。

| プレフィクス | 用途 |
|---|---|
| `add:` | 能力・ページの追加 |
| `fix:` | データ誤りの修正 |
| `chore:` | ツール・設定など、公開物に影響しない変更 |

例: `add: ロクショウの能力4件を追加`

- **push 先は `main`**（GitHub Pages の公開ブランチ）。
- 能力追加のコミットに `tools/` や `.claude/` の変更を混ぜない。

---

## 4. 承認フロー（重要）

**ユーザーの承認なしに push しない。** 手順4のチェックが通ったら、
次を提示して承認を待つ:

- 追加した能力の一覧（id / name / card / rarity / source / tags）
- 変更後の総件数と最大ID
- 更新表示の日付
- 新規カードを `*_CARDS` に追加したならその内容

承認が取れてから `git_commit_push.sh` を実行する。

## 5. トラブル対応

| 症状 | 対処 |
|---|---|
| `ABILITIES を検出できません` | 配列リテラルが壊れている。`git checkout -- index.html` で戻す |
| `JSONパースに失敗` | desc に生の改行か `"` のエスケープ漏れ。同上で戻してやり直す |
| `未知のタグ` | まず表記ゆれを疑う。正当な新タグなら `KNOWN_TAGS` に追加 |
| `更新表示の件数が一致しません` | `add_ability.py` を通さず手編集した可能性。件数を直す |
| `JS 構文エラー` | 文字列に `</script` か未エスケープの引用符が混入 |
| push が拒否される | `git pull --rebase origin main` してから再push |

**index.html を壊したら迷わず `git checkout -- index.html` で戻す。**
未コミットの追加分は失われるが、JSON を手直しして `add_ability.py` から
やり直すほうが確実に速い。
